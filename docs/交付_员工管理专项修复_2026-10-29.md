## 一、根因排查结论（先讲为什么）

| 现象 | 真实根因 |
|---|---|
| 角色显示英文、列重复 | 列表列是「按接口返回的第一个对象自动推导」出来的，把 `role`（英文码）和 `role_name`（中文）**当成两列同时显示**；部门/岗位/状态同理，共 4 组重复列 |
| 角色、状态下拉打不开 / 选项错乱 | ①部门、岗位、角色在自动表单里被推导成**纯文本输入框**（根本没有下拉）；②状态虽然是下拉，但选项来自全局 `FIELD_ENUM.status`（PENDING/ACCEPTED/…那套任务状态），**根本不是员工状态** |
| 状态总是「试用期」 | 不是显示问题——后端 `User.status` 默认值就是 `PROBATION`，7 个在职员工的库值确实是 `PROBATION`，从来没人改过 |
| 用户名显示手机号 | 导入/建号时 `username` 就是手机号，列表直接把 `username` 原样显示 |
| 员工编号空白 | 模型里 `employee_no`（工号）字段早就有，但**没有任何地方赋值**，全部为空 |
| 「质检」 | 是早期体检用的探测账号 `qa_probe`，显示名「质 检」（first_name=质 / last_name=检） |

## 五、遗留与提示

1. **工号从 EMP0002 开始**：EMP0001 属于已停用的「质 检」账号。按"编号不复用"原则不回收，新员工从 EMP0011 继续。
2. **「批量删除」按钮在员工管理页是坏的（历史遗留，非本次引入）**：`BaseListView` 会调用 `/accounts/users/bulk-delete/`，但员工接口继承的是普通 `ModelViewSet`，没有这个 action，实际返回 405。因涉及批量删账号且需保留"老板账号不可删"规则，本次未擅自改动，需要的话可单独做一版带规则的批量停用。
3. **员工状态的"自动转正"仍未做**：目前状态靠人事手动改（或走入转调离的转正流程）。如果希望"试用期到期自动转正式"，可以后续加定时任务，本次未擅自增加。
4. **工号格式**：`EMP0001`。若要改成"部门前缀 + 年份 + 序号"（如 `ACC26001`），改 `User.next_employee_no()` 一处即可。
